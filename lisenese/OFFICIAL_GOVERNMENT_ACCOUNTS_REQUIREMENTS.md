# متطلبات مشروع منصة إدارة الحسابات الرسمية
## Official Government Accounts Management Platform

> **حالة الوثيقة:** Source of Truth للمشروع الثاني  
> **هدف الوثيقة:** توثيق المتطلبات الوظيفية الكاملة للمشروع قبل إعداد خطة التنفيذ داخل النظام الحالي.  
> **مهم:** هذه الوثيقة تجمع بين متطلبات الملف الأصلي والملاحظات والتوضيحات اللاحقة من العميل. عند وجود تعارض، تُقدَّم التوضيحات اللاحقة.

---

# 1. نظرة عامة

المشروع عبارة عن منصة داخل النظام الحالي تهدف إلى **حوكمة ومتابعة حسابات الموظفين على المنصات الحكومية وشبه الحكومية**.

المقصود بالحسابات هنا ليس حسابات الدخول إلى نظام المستشفى نفسه، وإنما الحسابات التي يحصل عليها الموظفون من جهات أو منصات حكومية خارجية للقيام بمهام وظيفية معينة.

أمثلة:
- حساب للتقارير الطبية.
- حساب للإجازات الطبية.
- حساب للرخص الطبية.
- حساب لخدمة حكومية محددة.
- حساب بصلاحية معينة مثل مدقق أو معتمد أو مشرف.

الهدف من المشروع:
- معرفة كل حساب حكومي مرتبط بكل موظف.
- معرفة الجهة والخدمة والغرض من الحساب.
- معرفة حالة الحساب.
- معرفة من طلب الحساب ومن وافق عليه ومن نفذه.
- متابعة طلبات التعديل أو تغيير الصلاحية.
- متابعة طلبات الإيقاف والإغلاق.
- تنبيه المسؤولين عند تغير حالة الموظف الوظيفية.
- الاحتفاظ بسجل كامل لكل الطلبات والإجراءات.

يكون المشروع تحت إدارة **قسم التواصل المؤسسي**.

يدعم النظام:
- العربية والإنجليزية.
- RTL / LTR حسب اللغة.
- تصميم متوافق مع النظام الحالي.

---

# 2. مبدأ أساسي مهم

## النظام لا ينشئ الحساب الحكومي فعليًا

لا يوجد حاليًا تكامل مباشر مع الجهات الحكومية لإنشاء أو تعديل أو إيقاف الحسابات.

التدفق الصحيح:
1. يتم إنشاء الطلب داخل النظام.
2. يتم مراجعته واعتماده داخليًا.
3. يقوم قسم التواصل المؤسسي برفع الطلب إلى الوزارة / الجهة الحكومية خارج النظام.
4. الجهة الحكومية هي التي تنشئ أو تعدل أو توقف الحساب فعليًا.
5. بعد تنفيذ الجهة للطلب، يقوم التواصل المؤسسي بتحديث حالة الطلب والحساب داخل النظام.

إذًا دور النظام هو:
- الحوكمة.
- الطلبات والموافقات.
- المتابعة.
- التسجيل.
- التنبيه.
- التوثيق.
- Audit Trail.

ولا يجب افتراض وجود API حكومي حاليًا.

---

# 3. الفرق بين المستخدم الداخلي والحساب الحكومي

كل موظف في المستشفى لديه **مستخدم داخلي خاص به** داخل النظام.

أما الحساب الحكومي فهو سجل آخر مستقل مرتبط بالموظف.

لا يجب دمج الاثنين.

مثال:

الموظف: محمد أحمد  
المستخدم الداخلي: `mohamed.ahmed`

وقد يكون له حسابات حكومية مثل:
- منصة حكومية A — username: `MA001`
- منصة حكومية A — username: `MA_REPORT`
- منصة حكومية B — username: `MOH123`
- منصة حكومية C — username: `LICENSE45`

---

# 4. تعدد الحسابات

الموظف الواحد يمكن أن يمتلك:
- أكثر من حساب حكومي.
- أكثر من حساب في أكثر من جهة.
- أكثر من حساب داخل نفس الجهة.
- أكثر من حساب لنفس الجهة لكن لخدمات أو وظائف مختلفة.

قد يصل الموظف الواحد إلى عدة حسابات، مثل سبعة حسابات أو أكثر.

كل حساب يجب أن يكون **Record مستقل**.

لا يجب فرض Unique account per employee أو per authority بطريقة تمنع هذا السيناريو.

---

# 5. الجهات الحكومية

يجب إنشاء قائمة قابلة للإدارة للجهات الحكومية / الرسمية / شبه الحكومية.

لا توجد قائمة نهائية مطلوبة في الوقت الحالي.

يمكن إضافة بيانات أولية تجريبية ثم تعديلها لاحقًا.

يجب أن يستطيع المستخدم المخول:
- إضافة جهة.
- تعديل جهة.
- تعطيل جهة.
- إعادة تفعيل جهة.
- استخدام الجهة عند إنشاء طلب أو تسجيل حساب.

لا يجب كتابة أسماء الجهات Hardcoded في الكود.

---

# 6. الخدمات الحكومية

كل جهة قد تحتوي على خدمة أو أكثر.

مثال:
- التقارير الطبية.
- الإجازات الطبية.
- الرخص الطبية.
- خدمة أخرى.

يجب أن يستطيع مشرف التواصل المؤسسي:
- إنشاء خدمة.
- ربطها بجهة.
- تعديلها.
- تعطيلها.
- إعادة تفعيلها.

---

# 7. أنواع الحسابات / الأدوار / الصلاحيات الخارجية

الملف الأصلي يقترح وجود أسماء لصلاحيات الحساب مثل:
- مدقق.
- معتمد.
- مشرف.

لكن العميل أوضح أن **أنواع الحسابات يمكن تطويرها أو تنظيمها لاحقًا**.

بالتالي يجب تصميم النظام بحيث:
- لا تكون أنواع الحسابات Hardcoded.
- يمكن دعمها كمرجع قابل للتوسعة.
- لا يتم تعقيد هذا الجزء في المرحلة الأولى بدون حاجة.

الحد الأدنى المطلوب أن يستطيع الطلب تسجيل الدور / الصلاحية المطلوبة كقيمة منظمة أو قابلة للتعريف.

---

# 8. الأدوار الرئيسية داخل المشروع

## 8.1 رئيس القسم

يستطيع:
- إنشاء طلب حساب جديد.
- اختيار الموظف.
- اختيار الجهة.
- اختيار الخدمة.
- تحديد الدور / الصلاحية المطلوبة.
- كتابة سبب / مبرر الطلب عند الحاجة.
- قبول التعهد المطلوب منه.
- إرسال الطلب.
- متابعة حالة الطلب.
- مشاهدة سبب الرفض.
- تعديل الطلب أو الرد عليه وإعادة إرساله.
- إنشاء طلب تعديل حساب.
- إنشاء طلب تغيير صلاحية.
- إنشاء طلب إيقاف حساب.
- إنشاء طلب إغلاق حساب.

## 8.2 الموظف المعني بالحساب

هو الموظف الذي سيُنشأ أو يُعدل الحساب الحكومي له.

وفق متطلبات الملف الأصلي:
- يصل له إشعار بوجود طلب حساب.
- يمكن أن يظهر له تعهد إلزامي خاص بسرية الحساب والتدريب والمسؤولية.

> ملاحظة: يجب الحفاظ على تعهد الموظف كما ورد في الملف الأصلي ما لم يتم اعتماد قرار لاحق بإلغائه.

## 8.3 قسم التواصل المؤسسي

يستطيع:
- مراجعة الطلب.
- الموافقة.
- الرفض.
- كتابة سبب الرفض.
- استلام رد رئيس القسم وإعادة مراجعة الطلب.
- متابعة الطلب مع الجهة الحكومية.
- تسجيل أن الطلب تم رفعه للوزارة / الجهة.
- تسجيل أن الحساب تم إنشاؤه.
- تسجيل بيانات الحساب الفعلية.
- تسجيل تعديل الحساب.
- تسجيل إيقاف الحساب.
- تسجيل إغلاق الحساب.
- متابعة كل الحسابات والطلبات.
- إدارة الجهات والخدمات.
- إنشاء التنبيهات والاجتماعات / التدريبات.
- الاطلاع على السجلات والتقارير.

## 8.4 الموارد البشرية HR

المطلوب:
- صفحة للبحث عن الحسابات المفتوحة للموظفين.
- عند انتهاء علاقة الموظف الوظيفية أو الحاجة لإغلاق حساباته، يمكن رفع طلب إغلاق / إيقاف.
- الطلب يذهب للتواصل المؤسسي لمراجعته ومتابعته مع الجهة الحكومية.

## 8.5 Super Admin

يمتلك الرؤية والإدارة الكاملة حسب نظام الصلاحيات الحالي.

---

# 9. الإعدادات الأساسية للمشروع

يجب توفير إدارة للبيانات المرجعية التالية:
- الجهات الحكومية.
- الخدمات التابعة لكل جهة.
- أدوار / صلاحيات الحسابات الخارجية.
- حالات الطلبات.
- حالات الحسابات.
- أي قوائم مرجعية أخرى لازمة.

---

# 10. طلب إنشاء حساب جديد

يقوم رئيس القسم بإنشاء طلب حساب جديد ويحدد:
- الموظف.
- الجهة الحكومية.
- الخدمة.
- الدور / الصلاحية المطلوبة.
- سبب / مبرر الطلب إن وجد.
- أي ملاحظات.
- المرفقات إن وجدت.

---

# 11. تعهد رئيس القسم

تعهد رئيس القسم مطلوب حسب الملف الأصلي.

مضمونه:
- الموظف تم تدريبه.
- الموظف على دراية بالخدمة.
- تم الرد على أسئلته.
- رئيس القسم يتحمل مسؤولية رفع طلب إيقاف / تعديل الحساب عند الحاجة.

ومن الحالات التي تستوجب المتابعة:
- تغيير قسم الموظف.
- حصول الموظف على إجازة طويلة أو حالة تستوجب الإيقاف.
- انتهاء العلاقة الوظيفية.
- تغيير الوظيفة.
- تغير الدور الوظيفي.
- عدم الحاجة للحساب.

يجب حفظ:
- نص التعهد.
- المستخدم الذي وافق.
- التاريخ والوقت.
- الطلب المرتبط.

---

# 12. مصادقة / تعهد الموظف

حسب الملف الأصلي، بعد إنشاء الطلب يصل إشعار للموظف.

عند فتحه، يظهر تعهد الموظف.

مضمون التعهد:
- تلقى التدريب المطلوب.
- تم الرد على أسئلته.
- يحافظ على سرية الحساب.
- يستخدم الحساب للأغراض الوظيفية فقط.
- لا يشارك بيانات الدخول مع أي شخص.

بعد قبول التعهد:
- يتم تسجيل الموافقة.
- يتم تسجيل المستخدم.
- يتم تسجيل التاريخ والوقت.
- يتحرك الطلب للمرحلة التالية.

---

# 13. مراجعة التواصل المؤسسي

بعد اكتمال المتطلبات السابقة يصل الطلب إلى مسؤول / مدير التواصل المؤسسي.

يستطيع:
- الموافقة.
- أو الرفض مع سبب واضح وتعليق وتاريخ وهوية من رفض.

---

# 14. إعادة الطلب بعد الرفض

رفض الطلب لا يعني إغلاقه نهائيًا.

رئيس القسم يستطيع:
1. فتح الطلب المرفوض.
2. قراءة سبب الرفض.
3. تعديل البيانات إذا لزم.
4. كتابة رد.
5. إعادة إرسال الطلب.

ثم يصل الطلب مرة أخرى للتواصل المؤسسي.

يجب الاحتفاظ بكل جولات:
- Submission.
- Rejection.
- Response.
- Resubmission.

داخل Timeline.

---

# 15. رفع الطلب للجهة الحكومية

بعد موافقة التواصل المؤسسي:
- يتم تسجيل أن الطلب جاهز / تم رفعه للجهة.
- التواصل المؤسسي ينفذ الإجراء فعليًا خارج النظام مع الوزارة / الجهة.

يمكن تسجيل:
- تاريخ رفع الطلب.
- رقم مرجعي.
- ملاحظات.
- مرفقات.
- الجهة.
- المسؤول الذي نفذ الإجراء.

---

# 16. إنشاء الحساب بعد رد الجهة الحكومية

عندما تنشئ الجهة الحكومية الحساب فعليًا، يقوم التواصل المؤسسي بتحديث الطلب.

يتم تسجيل الحساب الحكومي كـ Record مستقل.

بيانات الحساب تشمل حسب المتاح:
- الموظف.
- الجهة.
- الخدمة.
- Username الخاص بالحساب.
- الدور / الصلاحية.
- تاريخ الإنشاء.
- حالة الحساب.
- رابط تسجيل الدخول إن وجد.
- رقم مرجعي إن وجد.
- ملاحظات.
- مرفقات عند الحاجة.

---

# 17. كلمات المرور

الهدف الأساسي للمشروع هو **حوكمة الحسابات ومتابعتها** وليس بناء Password Vault.

لذلك لا يجب افتراض تخزين كلمات مرور الحسابات الحكومية إلا إذا تم اعتماد ذلك صراحة.

إذا كان الملف الأصلي يتضمن حفظ "الرمز السري"، فهذه نقطة تحتاج قرار أمني قبل التنفيذ.

التوصية الافتراضية:
- تسجيل Username.
- تسجيل رابط المنصة.
- عدم تخزين Password بصيغة قابلة للقراءة.
- عدم إرسال Password عبر Email.

---

# 18. الإشعارات بعد إنشاء الحساب

بعد تسجيل أن الحساب تم إنشاؤه:
- يصل إشعار للموظف المعني.
- يصل إشعار لرئيس القسم يفيد بأن الطلب تم تنفيذه.

يجب ألا يتم إرسال معلومات حساسة لرئيس القسم لا يحتاجها.

---

# 19. حالات طلب الحساب

تصور مبدئي:
- Draft.
- Submitted.
- Awaiting Employee Confirmation.
- Under Corporate Review.
- Rejected.
- Resubmitted.
- Approved.
- Submitted to Authority.
- Waiting Authority.
- Completed.
- Cancelled.

الأسماء النهائية يمكن تبسيطها حسب أسلوب النظام الحالي.

---

# 20. سجل الحساب الحكومي

بعد اكتمال طلب إنشاء الحساب يتم إنشاء Government Account Record دائم مرتبط بـ:
- الموظف.
- الجهة.
- الخدمة.
- Username.
- Role / Permission.
- الحالة.
- تاريخ الإنشاء.
- الطلب الذي أدى لإنشائه.
- المسؤول عن متابعته.
- Timeline.
- الطلبات اللاحقة الخاصة بالتعديل / الإيقاف / الإغلاق.

---

# 21. حالات الحساب الحكومي

الحالات المنطقية تشمل:
- Pending.
- Active.
- Modification Requested.
- Suspension Requested.
- Suspended.
- Closure Requested.
- Closed.

لا يجب تعديل الحساب بشكل صامت بدون سجل طلب أو Audit.

---

# 22. طلب تعديل حساب

عندما يتغير:
- قسم الموظف.
- وظيفته.
- دوره.
- الصلاحيات المطلوبة.
- طبيعة عمله.

يتم إنشاء **طلب تعديل حساب**.

يمكن أن يشمل:
- تعديل الدور.
- رفع الصلاحية.
- تقليل الصلاحية.
- تعديل الخدمة.
- تعديل بيانات أخرى.

الطلب يمر عبر التواصل المؤسسي، وبعد تنفيذ الجهة يتم تحديث الحساب داخل النظام وتسجيل القديم والجديد.

---

# 23. طلب تغيير الصلاحية

يجب دعم:
- صلاحية أعلى.
- صلاحية أقل.
- دور مختلف.

ويتم تسجيل:
- الصلاحية الحالية.
- المطلوبة.
- السبب.
- من طلب.
- من وافق.
- النتيجة النهائية.

---

# 24. طلب إيقاف الحساب

يمكن طلب الإيقاف في حالات مثل:
- إجازة.
- نقل مؤقت.
- عدم الحاجة للحساب.
- تغيير وظيفة.
- قرار إداري.

الطلب لا يغلق الحساب تلقائيًا في الجهة الحكومية.

بعد تنفيذ الجهة يتم تحديث الحساب إلى Suspended.

---

# 25. طلب إغلاق الحساب

يستخدم عند:
- انتهاء عقد الموظف.
- انتهاء العلاقة الوظيفية.
- خروج الموظف.
- انتهاء الحاجة للحساب نهائيًا.

يمكن أن يبدأ من:
- رئيس القسم.
- الموارد البشرية.
- جهة مخولة أخرى.

ثم يذهب للتواصل المؤسسي.

بعد تنفيذ الجهة:
- الحساب Closed.
- يحفظ تاريخ الإغلاق.
- يحفظ السبب.
- يحفظ من نفذ المتابعة.

---

# 26. تكامل HR المستقبلي

العميل ذكر إمكانية توفير API من HR Portal لاحقًا.

الهدف:
- Refresh دوري.
- قراءة حالة الموظف.
- معرفة هل الموظف Active أم لا.

إذا كان الموظف Active:
- لا يحدث إجراء.

إذا لم يعد Active:
- النظام لا يغلق الحساب تلقائيًا.
- ينشئ Notification / Action Required.
- يظهر أن الموظف لديه حسابات حكومية تحتاج مراجعة / إيقاف.
- يصل التنبيه للأشخاص المسؤولين.

يجب تصميم النظام بحيث يمكن إضافة HR API لاحقًا بدون إعادة بناء المشروع بالكامل.

لكن لا يتم تنفيذ API وهمي حاليًا.

---

# 27. الموارد البشرية والحسابات المفتوحة

يجب توفير شاشة للموارد البشرية تسمح بـ:
- البحث باسم الموظف.
- عرض الحسابات الحكومية المفتوحة له.
- عرض الجهة.
- الخدمة.
- حالة كل حساب.
- رفع طلب إغلاق / إيقاف.
- كتابة السبب.

---

# 28. الاجتماعات والتدريب الخاصة بالجهات الرسمية

المشروع يشمل إدارة إشعارات الاجتماعات / التدريبات التي تنظمها الجهات الرسمية.

عند وجود:
- تدريب على خدمة جديدة.
- اجتماع.
- توجيه.
- دعوة.
- مناقشة مرتبطة بخدمة حكومية.

# 45. قواعد مهمة لتنفيذ الطلبات

# 51. ملاحظات مرجعية نهائية

- هذا الملف خاص بالمشروع الثاني فقط: **منصة الحسابات الرسمية**.
- الموظف الواحد قد يمتلك عدة حسابات حكومية.
- يمكن أن يمتلك عدة حسابات في نفس الجهة.
- كل حساب له غرض / خدمة / صلاحية مستقلة.
- كل موظف يستخدم مستخدمه الداخلي الخاص به للوصول للنظام.
- الجهات والخدمات قوائم قابلة للإدارة.
- التواصل المؤسسي يراجع الطلبات.
- التواصل المؤسسي يستطيع الرفض مع ذكر السبب.
- رئيس القسم يستطيع الرد وإعادة إرسال الطلب.
- تغيير القسم أو الوظيفة قد يؤدي إلى طلب تعديل / إيقاف الحساب.
- إيقاف / إغلاق الحساب يمر كطلب وليس تعديلًا صامتًا.
- الوزارة / الجهة الحكومية هي التي تنشئ أو تعدل الحساب فعليًا.
- لا يوجد تكامل حكومي مباشر حاليًا.
- HR API فكرة مستقبلية؛ عند عدم Active يتم إنشاء تنبيه ولا يتم الإغلاق التلقائي.
- الاجتماعات والتدريبات جزء مطلوب.
- المطلوب في الدعوات هو الإبلاغ وتسجيل المشاهدة.
- يجب تسجيل Viewed At عند فتح رابط الدعوة.
- المرفقات المطلوبة: PDF / Image / Excel.
- Timeline / Audit جزء أساسي.
